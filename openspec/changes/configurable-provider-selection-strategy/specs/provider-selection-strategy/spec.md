# 供应商选择策略

## ADDED Requirements

### Requirement: AC-001 配置持久化与旧配置兼容

系统 SHALL 提供全局 `provider_selection_strategy`，仅接受 `ordered` 与 `session_preferred`；默认及旧配置缺失字段使用 `session_preferred`。配置通过现有设置 API 保存并在重启后保留；修改其他设置不覆盖策略。非法值不得被当成合法策略保存。

#### Scenario: 旧配置与重启

- **WHEN** 读取不含策略字段的旧配置
- **THEN** 采用 `session_preferred`，其他配置保持原义
- **WHEN** 保存 `ordered` 并重启
- **THEN** 仍读取到 `ordered`

#### Scenario: 非法更新与无关更新

- **WHEN** 提交非法策略，或只修改另一个设置字段
- **THEN** 非法策略更新失败；无关更新保留已保存策略

### Requirement: AC-002 顺序优先恢复靠前供应商

在 `ordered` 模式下，每次可独立选路的新请求 SHALL 按当前有效分组和会话候选顺序快照，从最靠前的合格供应商开始；上次成功供应商不得旋转列表或改变候选起点。

#### Scenario: 额度恢复

- **GIVEN** 顺序为 A、B、C，A 不可用时上次请求在 B 成功
- **WHEN** A 已被现有门禁判定恢复可用，下一次可独立选路请求到来
- **THEN** 优先 A

### Requirement: AC-003 切换模型后重新从候选头部选择

在 `ordered` 模式下，系统 SHALL 先遵循现有模型过滤，再按剩余候选的基础顺序选择；失效绑定的清理不得使本次请求从旧供应商后面开始。

#### Scenario: GPT 切换 DeepSeek

- **GIVEN** 顺序为 A、B、C、D，A 支持 DeepSeek，B 支持 GPT，C 两者均支持；GPT 请求在 B 成功
- **WHEN** 下一次可独立选路请求使用 DeepSeek，A 与 C 均通过候选过滤和门禁
- **THEN** 优先 A，而不是 C

### Requirement: AC-004 保留会话优先行为

在 `session_preferred` 模式下，系统 SHALL 保留现有普通会话偏好，包括绑定供应商仍合格时的列表旋转，以及绑定被过滤时沿基础顺序寻找后续合格候选的行为；从 `ordered` 切回时不要求清空会话。

#### Scenario: 绑定供应商优先

- **GIVEN** 基础顺序 A、B、C，绑定 B 且 B 合格
- **WHEN** 以 `session_preferred` 处理续聊
- **THEN** 尝试顺序保持 B、C、A

#### Scenario: 绑定不支持本次模型

- **GIVEN** 基础顺序 A、B、C，绑定 B，本次候选仅含 A、C
- **WHEN** 以 `session_preferred` 处理普通续聊
- **THEN** 保留现有从 B 后面寻找 C 的行为

### Requirement: AC-005 保留候选过滤与失败切换保护

两种模式 SHALL 保留现有模型规则、显式指定供应商的校验、额度限制、冷却、熔断、失败切换与尝试预算。排序策略不得使不合格供应商进入候选；单次请求失败后不得因为顺序优先而重新启动一轮尝试。

#### Scenario: 靠前供应商仍受限或失败

- **WHEN** A 仍受额度、冷却或熔断限制，或 A 已按现有规则耗尽本次尝试
- **THEN** 按剩余候选继续，保留当前尝试预算

#### Scenario: 显式模型支持与通用兜底

- **WHEN** 现有模型规则排除靠前的通用兜底供应商
- **THEN** 两种模式均尊重过滤结果，不因其排序靠前而重新加入

### Requirement: AC-006 保存后的请求快照

系统 SHALL 在保存成功后让下一次进入路由的新请求使用新策略；已在途请求、流和单次请求的重试保持同一策略快照。切换不要求重启网关，也不清空会话、额度或熔断状态。

#### Scenario: 请求处理中切换

- **WHEN** 正在输出的请求期间保存另一策略
- **THEN** 该请求继续完成；下一次新请求采用新策略

### Requirement: AC-007 Codex 续接上下文归属

系统 SHALL 将普通会话偏好与经校验的 Codex 增量续接归属分开。仅靠请求含 `previous_response_id` 不构成可信绑定；依赖已有上游连接及响应标识的请求必须满足现有归属校验。具备完整上下文的独立请求按策略选路，不能为顺序优先把上游标识交给错误供应商。

#### Scenario: 有效增量续接属于 B

- **GIVEN** 策略为 `ordered`，A 排在 B 前，已校验续接上下文属于 B
- **WHEN** 请求必须依赖 B 的上游连接与响应标识
- **THEN** 保持必要的 B 归属，不向 A 发送属于 B 的续接标识

#### Scenario: 无效上下文

- **WHEN** 上下文缺失、标识伪造或归属不匹配且无法安全恢复
- **THEN** 返回现有上下文错误，不跨供应商发送该标识

### Requirement: AC-008 Codex 恢复不扩大尝试预算

系统 SHALL 复用现有安全恢复协议。只有满足现有恢复条件时才允许携完整上下文重新选路；按策略对允许的剩余候选排序，同时保留 generation 的失败集合、访问集合、剩余次数与截止时间约束，不复活已失败候选或重置预算。

#### Scenario: 上游失效后的安全恢复

- **WHEN** 原上游无法续接，且客户端满足现有完整重发与恢复授权条件
- **THEN** 在现有允许候选和剩余预算内选择供应商，保留既有排除和截止时间约束

### Requirement: AC-009 设置界面与路由说明

通用设置 SHALL 展示“供应商选择策略”，提供“顺序优先”和“会话优先”，说明续接可能保留必要归属。保存失败时显示错误并保留已保存值。现有诊断渠道必须能区分请求配置的策略与实际采用的会话偏好或上下文约束；`ordered` 普通请求不得被误报为会话复用。不得记录密钥、完整请求或提示词。

#### Scenario: 设置失败与普通顺序请求

- **WHEN** 保存策略失败，或处理不需要续接归属的 `ordered` 请求
- **THEN** 界面保留原值并提示失败；普通请求日志不宣称由上次供应商偏好选中
