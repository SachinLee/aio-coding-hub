# 供应商选择策略配置

## Why

当前供应商按客户端分组，分组内有固定候选顺序；续聊时会根据上次成功的供应商旋转列表。A 额度恢复后仍优先 B；GPT 使用 B 后切换 DeepSeek，即使 A 支持该模型，也可能从 B 后面的 C 开始。用户希望通过配置选择是否始终优先靠前的合格供应商。

## What Changes

- 新增全局 `provider_selection_strategy`，可选 `ordered`（顺序优先）与 `session_preferred`（会话优先）。
- 顺序优先保持过滤后的基础候选顺序；会话优先保留现有行为。
- 默认与缺失字段均使用 `session_preferred`，兼容旧配置；在客户端管理的通用设置中选择。
- 保存成功后下一次新请求生效；单次请求及其重试使用相同快照。
- 将普通会话偏好与 Codex 必要的上下文归属分开；保留安全恢复约束和已有失败切换预算。

## Capabilities

### New Capabilities

- `provider-selection-strategy`：配置、持久化、请求排序、续接例外与界面行为。

### Modified Capabilities

- 无现有 OpenSpec 基准规范；新增能力规范描述本次完整增量要求，不改写历史任务。

## Impact

Rust 设置与 IPC、运行时设置、供应商选择、Codex WebSocket 续接、TypeScript 设置映射及通用设置界面、相关测试和生成绑定。复用已有链路，不增加依赖、调度服务或数据库表。

## 目标与边界

范围内：策略配置、两种路由行为、旧配置兼容、热生效、续接安全、日志语义和回归验证。

范围外：改变客户端分类；按模型或客户端单独配置；强制同步已有会话的最新拖拽排序；余额轮询与自动解除所有冷却；新负载均衡算法；重构整个会话管理；修改 `.workflow/`、`.trellis/` 或远端状态。

假设：顺序以会话当前有效分组及候选顺序快照为基础；沿用现有模型过滤（包括显式支持优先于通用兜底）。供应商被系统判定恢复可用后才保证重新优先；完整上下文与增量续接由既有协议状态判断。

## 风险与授权

实施档位：`critical`。原因是持久化配置兼容、IPC 类型以及跨层 Codex 上下文归属和恢复预算；新增策略不得损坏旧配置或把上游响应标识送给错误供应商。

本轮操作仅为文档初始化与记录，按 `lightweight` 验证产物结构。用户已确认初始化 OpenSpec 并创建 `configurable-provider-selection-strategy`。此确认不代表方案批准、实施许可、验收或归档；当前方案待批准。
